# 方向一：近期落地 · 不依赖AI

通过清晰的目录、表单、规则校验、监控和操作记录改善体验，不依赖AI助手。以下为可进入需求细化的设计方案，具体交付范围仍需按版本确认。

## 双门户分工，业务模块组织入口

Portal围绕项目、开发环境、数据、训练、模型和推理服务组织目录；Admin围绕资源、调度、监控、故障、运营和安全组织目录。工作台提供常用场景入口，按角色授权显示菜单。

预期结果：用户能从自己的任务找到入口，三员职责分离，管理员不默认获得业务数据查看权限。

## 串起任务步骤，明确完成结果

通过表单、模板和规则校验，检查输入、版本、资源和权限；在开发、训练与部署页面之间携带已选对象，显示进度、日志、结果与下一步入口。已有模型可直接部署，已有服务可直接调用。

预期结果：用户知道准备什么、当前卡在哪里、任务是否完成，减少重复填写和页面往返。

## 连接告警与任务，处理后验证恢复

关联告警、设备、受影响任务和时间记录，提供日志、检查项与标准处置入口；业务恢复和设备复验分别记录，明确负责人、处理状态和交接信息。

预期结果：管理员能判断影响、按规程处理并确认恢复，保留完整操作记录。

## 贯通资源与用量，明确管理责任

按项目展示资源配额、已分配资源、实际用量及费用，统一统计口径和时间范围；资源申请、配额调整、回收及费用核对采用明确的审批和操作记录。

预期结果：用户看清授权范围与使用情况，运营管理员能核对费用和资源去向。

# 超节点设计策略方向

四个高层方向与十四项执行方案分层；AI均为待验证设计提案，实际能力与交付范围另行确认。

## 1 从功能入口，转向目标驱动的人机协作

- 方向编号：goal-copilot
- 设计策略方向：从功能入口，转向目标驱动的人机协作
- 体验转变：从用户自己找菜单、拼参数，转向用户说明目标、AI协助准备计划、系统校验后执行。
- 根本问题：完成一项任务需要跨越资源、环境与专业组件，用户容易遗漏前置条件，也难判断一次操作是否真正完成。
- 设计原则：以目标组织任务，用结构化计划和执行回执连接界面，AI负责提议，确定性系统负责校验与执行。
- 创新点：待验证提案：将目标转换为包含对象、输入版本、资源条件、动作、依赖、验证方式和出口的任务计划；缺少信息先指出，用户可修改。计划按当前身份呈现可执行步骤、协作交接和执行回执。
- 人机协作流程：人：说明目标与约束（选择训练、交付或资源申请目标，确认项目、输入、资源约束与期望结果。） → AI：形成结构化草案（在获准资料范围内组织任务步骤，标明缺项、假设和需要专业组件提供的能力；不推测未知参数。） → 系统：逐项校验（校验身份、权限、版本兼容、资源和依赖，不能通过的步骤返回具体原因；不由语言模型代替规则判断。） → 人：确认动作与交接（检查目标、配置差异和影响对象；高风险变更交获授权责任人确认，越权步骤交对应职责处理。） → 系统：执行并核对结果（调用受控接口或跳到获准专业页面，记录执行回执；检查验证条件是否满足，明确未完成项。）
- 人工决定与系统边界：这是AI参与方式的设计提案。AI不授予权限、不绕过三员、不自行承诺资源或交付时间。执行前必须通过确定性校验；高风险操作由有权限的人确认，全部执行与确认纳入审计。
- 实现前提：结构化任务与模板规范；权限与项目范围接口；兼容矩阵和资源状态；专业组件深链与SSO；执行回执和验收规则。
- 试用任务：让用户准备一项带缺失输入的训练任务，另让管理员准备存在兼容问题的交付计划。
- 现场观察：用户能否发现AI计划缺项、理解被阻塞原因、修改草案并找到责任人；系统是否阻止无权限或不兼容动作。
- 有帮助的判断：计划与用户目标一致，缺项和阻塞没有被隐藏；用户能够说明下一步，系统只执行校验通过且已完成必要确认的动作，并保留结果。尚未实测，不预设提速比例。
- 执行项：role-entry；intent-execution-result；independent-hardware-portal；deployment-delivery-loop
- 原图编号：baidu-06；baidu-08；ahr-07
- 方案状态：本项目待验证设计提案；竞品实现与版本交付分别核实

## 2 从监控看板，转向证据驱动的可信运维

- 方向编号：evidence-recovery
- 设计策略方向：从监控看板，转向证据驱动的可信运维
- 体验转变：从分散看告警、凭经验转派，转向保留任务和时间上下文，以可核对证据组织诊断与恢复。
- 根本问题：设备、网络、缓存和设施异常分散在不同视图；业务恢复后，原设备可能仍未修好，错误判断容易造成误回池。
- 设计原则：先确认影响与证据，再讨论原因和动作；事实、推断、处置及验证结果必须分开。
- 创新点：待验证提案：AI汇总授权范围内同一时间窗的日志、指标和拓扑关系，生成带来源的原因假设、缺失证据和下一项检查；系统校验动作前置条件，恢复页并列业务恢复和硬件维修，不能由AI把未知标成正常。
- 人机协作流程：系统：固定对象与时间窗（记录异常任务、设备、链路和数据时间，显示过期、未知与缺失状态。） → AI：提出带来源的原因假设（按事实、推断与待检查项组织诊断，逐项引用来源；证据不够时保留未知，不声称已找到唯一根因。） → 人：核对影响与处置方案（责任人核对关键证据、影响业务、候选动作与风险，决定追加检查或进入恢复。） → 系统：校验并受控执行（确认权限、对象、隔离范围与操作前提；高风险动作经授权确认后执行，全程审计。） → 系统与人：分别验证业务和硬件（记录任务恢复与设备复测结果，依确定性规则回池；失败留在未完成分支，现场维修按职责交接。）
- 人工决定与系统边界：AI诊断呈现待核实的原因假设，执行权限由既定授权规则校验。AI新提出的断电、隔离、换件与网络变更按风险及既定规则交授权人确认；物理控制仍由对应模块执行。已获授权的确定性复测、回池按既定规则自动执行并保留审计和回执，不额外增加人工审批，也不允许AI修改通过条件。
- 实现前提：任务资源与稳定设备标识；统一时间、遥测与日志来源；拓扑和业务影响关系；故障隔离与恢复接口；设施SOP和控制责任；复测规则与审计记录。
- 试用任务：在测试环境重现训练变慢、通信故障和设备维修后复测失败，并混入缺失或过期指标。
- 现场观察：用户能否从建议追到原始证据、区分事实与假设；是否能识别未知；任务恢复后是否仍保留设备维修状态。
- 有帮助的判断：诊断来源可查，无法确认的原因保持待查；越权或前提不足的操作被阻止；业务与设备结果分别记录，复测失败不会被表示为健康回池。效果尚待验证。

- 方案状态：本项目待验证设计提案；竞品实现与版本交付分别核实

## 3 从单次任务，转向可复用的成果交付

- 方向编号：reusable-delivery
- 设计策略方向：从单次任务，转向可复用的成果交付
- 体验转变：从交接模型文件和手工重配环境，转向可追查的输入、运行、产物与服务交付链。
- 根本问题：模型、数据、镜像和参数分开维护，复现实验或部署服务时难以判断版本是否一致，外部调用成功与实例就绪也容易混淆。
- 设计原则：复用成功条件而非照搬参数；每次复用都核对版本差异、兼容条件和目标验证。
- 创新点：待验证提案：AI从已获准的成功任务和模型记录提出可复用配置，列明版本差异与未知依赖，协助生成部署交接清单；系统校验后形成任务或服务版本。已有模型允许直接部署，外部应用只做获授权API接入，不强迫经过训练或内置Agent编排。
- 人机协作流程：人：选择成果与新目标（选择已有模型或成功实验，说明继续训练、评估或服务化的目标。） → AI：整理复用条件和差异（从可查记录组织数据、代码、镜像、参数和资源条件，标明不能确认或需要变更的部分。） → 系统：校验新版本配置（核对访问权限、资产版本、兼容性和资源条件，提交前给出确定的通过或失败结果。） → 人与系统：执行并验证目标（用户确认适用配置，系统创建任务或部署；分别检查产物评估、实例健康和请求结果，高风险变更单独确认。） → 人：完成版本交接（接收者确认模型版本、条件与验证记录；外部应用核对本人Key和简单调用，保留审计与问题交接。）
- 人工决定与系统边界：AI不推造缺失的血缘、模型质量或兼容性，不因历史成功自动批准新部署。配置修改通过确定性校验，生产升级和流量变更按风险由授权人确认并审计。外部编排不进入第三门户。
- 实现前提：资产版本和输入快照；代码镜像模型血缘；成功与失败运行记录；兼容性和服务部署接口；评估与调用验证方法；Key范围及变更审计。
- 试用任务：让用户复用一次模型实验，但替换数据或镜像版本；另从已有模型直接部署服务并交给外部调用方。
- 现场观察：用户能否找到差异并作出选择；是否明确评估、实例健康和调用结果；交接方是否能追查输入和运行条件。
- 有帮助的判断：未验证兼容条件不会被当成成功继承；模型可追到真实输入和任务，部署与调用分别验证；使用已有模型不被要求重复训练。尚未实测复用效率。

- 方案状态：本项目待验证设计提案；竞品实现与版本交付分别核实

## 4 从资源管理，转向可追责的经营治理

- 方向编号：accountable-governance
- 设计策略方向：从资源管理，转向可追责的经营治理
- 体验转变：从只看占用和金额，转向按主体追查使用、规则、决策与执行结果。
- 根本问题：额度、实际分配、利用率和费用口径混杂；跨项目或集群调整后难确定是谁批准、是否生效以及成本如何归属。
- 设计原则：建议可解释、规则可复查、执行有边界；运营效率不以合并系统、安全与审计职责换取。
- 创新点：待验证提案：AI把资源、消耗和账单差异整理成带依据的复盘卡，说明影响主体、适用价格版本、缺失数据及待决规则；提出额度或容量建议，由确定性计量计费和授权体系验证，责任人确认后才改变资源。跨集群先解释边界，不让AI自行进行未获准放置。
- 人机协作流程：系统：建立主体与规则依据（关联项目、任务、服务、资源和计量，保留价格版本、权限范围与执行记录。） → AI：解释差异并提出建议（在授权数据内比较额度、使用和费用，列出已确认差异、缺失项与候选调整，未定收费规则不补算。） → 人：按职责核对与决策（用户核对本项目，运营核对商业规则，安全审核权限；跨集群或容量变更由相应授权责任人确认。） → 系统：规则校验与执行回执（对额度、计价、作用范围和资源条件确定性校验；高风险调整确认后执行并记录实际生效结果。） → 审计员与责任人：复核结果并留存（独立追查建议、批准和执行，确认差异处理；用量报表、账单核对与结算数据分开留存。）
- 人工决定与系统边界：AI不签发权限、不改价格、不补造缺失计量、不自动决定商业结算。系统、安全、审计互斥；运营为可选扩展。高风险变更必须经授权确认、确定性校验并全程审计，财务只读核对。
- 实现前提：计量主体与数据完整性；价格规则和账单版本；三员权限矩阵与复核流程；额度与实际分配回执；跨集群能力和数据位置；审计与对账修订规则。
- 试用任务：提供费用突增、缺失计量、项目额度未生效和跨集群范围不匹配的测试案例，让不同职责人员协作处理。
- 现场观察：用户能否沿解释查到原始明细和规则，识别未知项；安全与审计是否仍保持独立；实际变更是否有回执。
- 有帮助的判断：缺失不被记为零或补造金额；建议能追查依据，未授权变更被阻止；批准与执行不混淆，审计可独立复核，账单确认不显示成已支付。收益尚待真实验证。
- 执行项：meter-cost；authorization-audit；multi-cluster
- 原图编号：runai-02；baidu-32；sothis-26
- 方案状态：本项目待验证设计提案；竞品实现与版本交付分别核实
